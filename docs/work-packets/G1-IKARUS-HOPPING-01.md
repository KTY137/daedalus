## Acceptance claim

Ikarus can request an isolated Genesis build through the existing computer
Mission/effect boundary. New Genesis evaluations compile the same candidate's
Fourfold into the existing typed tensor relation kernel and retain the result
as evidence. Ariadne can use an explicitly owner-configured frozen test profile,
not model-selected test commands. Every campaign projection distinguishes a
candidate nomination from eligibility to switch the running installation.

This packet does NOT claim automatic activation, a secure hostile-code sandbox,
unlimited code generation, live desktop parity, or superior tensor retrieval.
Hopping activation remains blocked: the current pytest verdict is self-reported,
the candidate child lacks an egress fence, and promotion remains sealed. No
candidate may alter its evaluator, policy, approval or promotion authority.

## Scope and invariants

Extend the existing computer tool registry, injected runner composition, Genesis
service, Ariadne adapter, tensor projection and their focused tests. No parallel
scheduler, event store, candidate identity or promotion path. Fresh setup grants
no tools. Genesis gets its own explicit build grant; it does not ride the read-only
Daedalus grant. Test profiles live in the checkout-external canonical control
root, are bounded and immutable for a campaign, and require explicit risk acknowledgement.
No changes to the master plan, amendment chain, AGENTS or existing release fences.

## Frozen acceptance matrix

- Existing tensor and contraction tests remain green; exact source/candidate
  binding, wrong Forest digest and partial endpoint planes are tested.
- Genesis tensor output is retained in the canonical EvidencePacket; a tensor
  compiler failure prevents a green round trip. No fabricated completeness.
- The computer tool executes the canonical Genesis runner, not a new builder;
  unknown arguments, missing runner, missing grant and malformed results refuse.
- No model-supplied host paths, publish flags, test argv or control policy.
- Cancellation/policy checkpoints before entry and after return; existing kernel
  kill-switch remains active during child execution. No blind retry of unknown effects.
- Owner test profile changes change campaign identity; no fallback to exact match
  when test execution was requested but admission failed.
- Hopping projection is advisory and fail-closed for weak, missing or stale evidence;
  a boolean success or nomination cannot authorize switching.
- Default grants and existing SCC structure remain unchanged (only tool inventory grows).
