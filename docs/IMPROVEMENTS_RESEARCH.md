# Token-Saving & Architecture Research for `agent_env` Orchestration Harness

Date: 2026-07-05
Researcher: Prometheus (researcher agent)
Scope: pure research, no code/config changed. Target system: local multi-agent
harness — Claude senior orchestrator (7 specialist roles) + "Ikarus" foreman
spawning Ollama qwen2.5-coder:7b workers for low/mid-risk work, dormant DeepSeek

## 1. Token-saving techniques, ranked by impact/effort for this design

| # | Technique | Impact | Effort | Notes |
|---|---|---|---|---|
| 1 | **Prompt caching (cache_control breakpoints)** | High (up to 90% off cached input tokens; stacks with batching for ~95% off) | Low | Anthropic: cache reads cost 0.10x input, writes 1.25x (5-min TTL) or 2.0x (1-hr TTL); minimum cacheable block is 1,024 tokens; must place stable content (system prompt, tool defs, `docs/ARCHITECTURE.md` excerpts) *before* per-call dynamic content, and the client must actually set `cache_control` — many clients silently don't. **[official docs]** [Anthropic prompt caching](https://docs.claude.com/en/docs/build-with-claude/prompt-caching), analysis: [ngrok blog](https://ngrok.com/blog/prompt-caching), [hidekazu-konishi.com](https://hidekazu-konishi.com/entry/anthropic_claude_api_prompt_caching_and_token_efficiency.html) **[secondary]** |
| 2 | **LLM cascades (FrugalGPT pattern)** | High (up to 98% cost cut vs. best single model, sometimes +4% accuracy) | Low-Med | Cascade = try cheapest/local model first, score the answer, escalate only on failure. This *is* your dual-gate design already; the missing piece is an automated **quality gate** before accepting a local answer (not just risk-tier routing). **[paper]** [FrugalGPT arXiv:2305.05176](https://arxiv.org/abs/2305.05176), [TMLR 2024 version](https://lingjiaochen.com/papers/2024_FrugalGPT_TMLR.pdf) |
| 3 | **Structured-output / JSON-schema contracts at every hand-off** | Med-High (cuts parse-failure retries from ~8-15% to <0.1%) | Low | You already have `AGENT_PROTOCOL.md` JSON report contracts — formalize with schema validation + exactly one deterministic re-ask before any provider escalation, so malformed local output doesn't silently trigger a Claude fallback. **[secondary]** [structured output reliability stats](https://www.cognitivetoday.com/2025/10/structured-output-ai-reliability/), [agenta.ai guide](https://agenta.ai/blog/the-guide-to-structured-outputs-and-function-calling-with-llms) |
| 4 | **Context pruning / compaction for long sessions** | Med-High for long-running sessions | Med | Pruning to "last N tool call/response pairs + rolling summary" gave +8pp task performance *and* -63.9% tokens in one study; separately, "context rot" studies show degradation starting past ~30k tokens even in large-context models — argues for aggressive compaction regardless of window size. **[paper]** [Less Context, Better Agents arXiv:2606.10209](https://arxiv.org/pdf/2606.10209), context-rot claim: [Zylos research](https://zylos.ai/research/2026-02-28-ai-agent-context-compression-strategies/), Microsoft's built-in compaction: [Microsoft Learn](https://learn.microsoft.com/en-us/agent-framework/agents/conversations/compaction) |
| 5 | **Batch API for offline/non-interactive Claude jobs** | Med (only applies to non-latency-sensitive work) | Low | 50% off standard tokens, stacks with cache reads (still 50% off cached tokens too) → ~95% off for repeated-system-prompt batch jobs. Good fit for nightly full-repo QA audits or docs regeneration, not for interactive dispatch. **[official docs]** [Anthropic Message Batches API](https://www.respan.ai/articles/anthropic-message-batches-api), [Claude batch guide](https://www.codewords.ai/blog/anthropic-batch-api) |
| 6 | **Router-by-difficulty (train a cheap classifier instead of keyword scoring)** | Med, but data-hungry | Med-High | RouteLLM's approach (BERT classifier / matrix-factorization on human-preference data) beat keyword heuristics: -85% cost on MT-Bench, -45% on MMLU, -35% on GSM8K vs. GPT-4-only, at matched quality. Requires labeled preference data you don't yet have — worth prototyping later, not a first move given the zero-dep philosophy. **[official docs/paper]** [RouteLLM blog](https://www.lmsys.org/blog/2024-07-01-routellm/), [repo](https://github.com/lm-sys/RouteLLM) |
| 7 | **Semantic caching (GPTCache-style) for repeated/similar read-only queries** | Med, narrow scope | Med | Only safe for advisory/read-only queries (never for code-mutating asks) because of well-documented false-positive risk: false-hit rate climbs once embedding quality is exceeded (>3-5%), reranking cuts false-positive cache-hits 60-80% at 15-30ms cost, and long conversation histories create false semantic overlap across sessions — cap at short conversation windows. **[secondary]** [Portkey semantic caching thresholds](https://portkey.ai/blog/semantic-caching-thresholds/), [TrueFoundry: why cache keys are wrong by default](https://www.truefoundry.com/blog/semantic-caching-llm-gateway), [PyImageSearch TTL/cache-safety](https://pyimagesearch.com/2026/05/04/semantic-caching-for-llms-ttls-confidence-and-cache-safety/) |
| 8 | **RAG-to-avoid-reloading (index `docs/ARCHITECTURE.md` etc. instead of pasting in full each call)** | Low-Med for a repo this size | Med | Given the repo's docs are small (a handful of markdown files), a full RAG pipeline is likely over-engineering; prompt caching (#1) on the same static docs achieves most of the same savings with far less complexity. Only worth it if `docs/` grows to the point caching's 1,024-token minimum stops mattering. No strong primary source specific to small-repo case — inference from cache-vs-RAG cost comparisons above. **[secondary, inference]** |
| 9 | **Speculative routing / speculative decoding** | Low fit here | High | Real speculative decoding (draft-model proposes tokens, big model verifies in bulk) targets *latency* inside a single model family with shared vocab, not cross-provider (Ollama-vs-Claude) cost routing — not applicable to this architecture as-is. **[paper]** [WhiFlash arXiv:2606.07710](https://arxiv.org/pdf/2606.07710) |

## 3. Modularity / architecture patterns (concrete, not platitudes)

- **Provider seam = abstract base class + factory/registry map**, not `if/elif` chains. Pattern seen consistently across LiteLLM-style gateways: a `BaseProvider`/`LLMProvider` ABC defines `chat()`, `stream()`, `tool_schema()`; a factory map (`{"claude": AnthropicProvider, "ollama": OllamaProvider, "deepseek": DeepSeekProvider}`) instantiates by name from config, so adding a provider = one new class + one registry line, no router-logic edits. **[secondary]** [LLM Gateway Core provider overview](https://www.mintlify.com/anaslimem/llm-gateway-core/providers/overview)
- **Config-driven routing tables, not code-embedded rules.** LiteLLM's `router_settings` (model groups + `fallbacks` list + `routing_strategy` enum) and RouteLLM's `--route-only` flag (evaluate routing decisions without touching real provider endpoints/API keys) are both examples of separating *policy* (data) from *mechanism* (code) — directly testable: you can unit-test the router against fixture briefs with no network calls. **[official docs]** [LiteLLM routing docs](https://docs.litellm.ai/docs/routing-load-balancing), **[repo]** [LLMRouter architecture](https://ulab-uiuc.github.io/LLMRouter/learn/architecture/)
- **Capability/interface-based routing over model-name routing.** Route on declared capabilities (`can_edit_files`, `can_run_tools`, `max_context`, `data_sensitivity_cleared`) rather than hardcoding "qwen2.5-coder" vs "claude" by name, so swapping the local model (e.g., to qwen3-coder or devstral later) doesn't require touching routing logic — matches LLMRouter's stated goal of swapping KNN→GNN→LLM-based routers "without changing the surrounding CLI/workflow." **[secondary]** [LLMRouter architecture](https://ulab-uiuc.github.io/LLMRouter/learn/architecture/)
- **`route_single`/`route_batch` as the only router contract** — keeps the router itself a pure function (state in, decision out) that's trivially unit-testable in isolation from the actual provider calls, mirroring the conditional-edge-router idiom in LangGraph (`router(state) -> node_name`). **[official docs]** [LangGraph add_conditional_edges](https://reference.langchain.com/python/langgraph/graph/state/StateGraph/add_conditional_edges)
- **Explicit quality/eval gate before trusting a routing decision in production**, sized at 50-500 fixture cases — this is the mitigation practitioners cite against the "silent escalation" failure mode (see §4) and doubles as your regression test suite for the router itself. **[secondary]** [merge.dev LLM routing overview](https://www.merge.dev/blog/llm-routing)
- **Batch/offline vs. interactive paths should be separate code paths**, since batch APIs (50% off) require async submit/poll semantics incompatible with an interactive dispatch loop — don't try to force one router abstraction to cover both without a mode flag. **[official docs]** [Anthropic batches guide](https://www.codewords.ai/blog/anthropic-batch-api)

## 4. What practitioners say (2025-2026)

- **Local coder models for agentic edit/tool-use work, state of practice mid-2026:** qwen2.5-coder:7b is a small/older tier by mid-2026 standards; current recommendations for serious agentic coding trend toward **Devstral Small 24B** (purpose-built for tool calling/multi-step workflows) or **Qwen3-Coder** (MoE, 3B active/80B total, reported comparable to Claude Sonnet on some agentic-coding benchmarks) as of Feb 2026 releases. This suggests re-benchmarking whether qwen2.5-coder:7b is still the right low-risk-lane model, or whether a newer same-size-class model now does meaningfully better at tool-use reliability for the same VRAM/latency budget. **[secondary]** [Qwen3-Coder guide](https://dev.to/sienna/qwen3-coder-next-the-complete-2026-guide-to-running-powerful-ai-coding-agents-locally-1k95), [best local LLMs 2026](https://www.promptquorum.com/local-llms/best-local-llms-for-coding), [QwenLM/Qwen3-Coder repo](https://github.com/QwenLM/Qwen3-Coder)
- **The "silent escalation" cost-routing gotcha** (most load-bearing practitioner finding for this project): a router sent simple work to a cheap model, verified output with a schema check, and escalated on failure — a provider-side format change silently broke the schema check, so ~90% of traffic quietly escalated to the most expensive model with **no error, no alert**, and cost savings evaporated unnoticed. Mitigation cited: a pre-merge/pre-deploy eval gate of 50-500 fixture cases run against the verifier itself, not just the router. Directly relevant because this project's stage-2 gate has the same shape (schema/verifier gates local-model output before accept/escalate). **[secondary]** [digitalapplied.com LLM routing 2026](https://www.digitalapplied.com/blog/llm-model-routing-2026-cost-quality-optimization-engineering-guide)
- **Cheap-model routing backfires on deep reasoning / long-context / careful instruction-following tasks**, and frequent fallback-on-failure can increase both latency and total cost if the cheap tier fails often — argues for keeping change-risk tiering (as this project already does) rather than a pure cost-minimizing router. **[secondary]** [merge.dev LLM routing overview](https://www.merge.dev/blog/llm-routing)
- **Naive "route to cheapest" without provider-diversity awareness saturates the cheap path first under load** — OpenRouter's own postmortem-style write-up notes the cheapest provider is also first to degrade/slowest to recover; inverse-square price weighting plus per-provider outage deprioritization is their fix. Less directly applicable (single local model, no multi-provider pool) but relevant if the DeepSeek lane is ever activated alongside Ollama. **[official docs]** [OpenRouter model routing mechanics](https://openrouter.ai/blog/insights/model-routing/)
- **Semantic cache false-positive risk in conversational/agentic contexts**: long conversation histories create high semantic overlap across unrelated sessions, causing wrong-answer cache hits; practitioners suggest capping semantic caching to short conversations (~3-5 turns) and/or adding a reranking step. Reinforces recommendation to keep semantic caching (if adopted) restricted to short, stateless advisory queries only. **[secondary]** [getmaxim.ai semantic caching](https://www.getmaxim.ai/articles/how-to-optimize-llm-cost-and-latency-with-semantic-caching/), [truefoundry semantic caching](https://www.truefoundry.com/blog/semantic-caching-llm-gateway)
- **Context rot**: agent performance degrades measurably past ~30k tokens of context even in models with much larger nominal windows, independent of hitting the hard limit — an argument for compaction as a quality lever, not just a cost lever. **[secondary]** [Zylos context compression research](https://zylos.ai/research/2026-02-28-ai-agent-context-compression-strategies/)

## 5. Ranked recommendations for THIS design (top 6)

1. **Add an automated quality/verifier gate before accepting local-model (low-risk) output**, distinct from the existing risk-tier routing — cheap deterministic checks (schema validation, lint, existing test suite) run on every local-write before it's considered done; anything that fails escalates to the mid-risk "local reads+advises, senior applies" path instead of silently retrying forever or shipping bad output.
   - Impact: High — this is exactly the mechanism FrugalGPT cascades rely on for cost savings, and it's the specific gap practitioners say causes the "silent escalation" failure mode (§4) that erases savings unnoticed.
   - Effort: Low-Medium (a few validators + a log/alert on repeated failures).
   - Borrow from: FrugalGPT cascade pattern ([arXiv:2305.05176](https://arxiv.org/abs/2305.05176)); "eval gate of 50-500 fixture cases" mitigation ([digitalapplied.com](https://www.digitalapplied.com/blog/llm-model-routing-2026-cost-quality-optimization-engineering-guide)).

2. **Structure every Claude call for prompt caching**: put static content (persona system prompt, tool schemas, `docs/ARCHITECTURE.md` excerpts) first and behind explicit `cache_control` breakpoints, dynamic per-task content last; confirm the `claude` CLI actually sets `cache_control` for repeated stable blocks (many clients don't by default).
   - Impact: High — up to 90% off cached-input tokens on every Claude call; this project makes many small Claude calls with shared context (persona + architecture docs), the ideal caching shape.
   - Effort: Low — reordering + a config check, no new dependency.
   - Source: [Anthropic prompt caching docs](https://docs.claude.com/en/docs/build-with-claude/prompt-caching).

3. **Formalize the AGENT_PROTOCOL.md JSON report contract with schema validation + exactly one deterministic re-ask on parse failure**, before any provider-escalation is considered.
   - Impact: Medium-High — avoids wasting a Claude escalation on a malformed-but-fixable local response; structured-output enforcement drops JSON parse failures from ~8-15% to <0.1% in practice.
   - Effort: Low — you already have the JSON contract; add a schema + retry-once rule at the intake boundary.
   - Source: [structured output reliability stats](https://www.cognitivetoday.com/2025/10/structured-output-ai-reliability/).

4. **Adopt llama-swap's config pattern (or the tool itself) for the Ikarus/Ollama lane** to run multiple local models behind one endpoint (e.g., a tiny model for stage-1/2 routing classification, qwen-class model for edits) with hot-swap instead of hand-rolled process spawning.
   - Impact: Medium — enables a near-zero-cost local classifier for the routing decision itself (see semantic-router idea below), and simplifies multi-model local ops.
   - Effort: Low-Medium — single static Go binary, MIT license, YAML config, no Python dependency conflict.
   - Source: [llama-swap repo](https://github.com/mostlygeek/llama-swap), MIT license confirmed.

5. **Replace/augment stage-1 keyword-and-path scoring with a small embedding-based router (`semantic-router` pattern)** — route by nearest-example-utterance similarity instead of brittle keyword matching, at near-zero token cost since it's a local embedding lookup, not an LLM call.
   - Impact: Medium — improves stage-1 routing accuracy without spending any model tokens on the routing decision itself.
   - Effort: Medium — need to define per-role example utterances/routes, but the library is MIT and small.
   - Source: [aurelio-labs/semantic-router](https://github.com/aurelio-labs/semantic-router), MIT.

6. **Add context compaction (pruning to last-N tool call/response pairs + rolling summary) for any long-running Ikarus or Claude session**, both for cost and because context rot degrades quality past ~30k tokens regardless of nominal window size.
   - Impact: Medium-High for long sessions (documented -63.9% tokens, +8pp performance in one study), low relevance for short one-shot dispatches.
   - Effort: Medium — needs a summarization step and a "keep last N" policy per session type.
   - Borrow from: Microsoft Agent Framework's built-in compaction feature as a reference design ([MS Learn compaction docs](https://learn.microsoft.com/en-us/agent-framework/agents/conversations/compaction)); pruning study ([arXiv:2606.10209](https://arxiv.org/pdf/2606.10209)).

**Not recommended right now** (noted for completeness): semantic response caching (GPTCache-style) — real false-positive risk for anything code-mutating, only consider for read-only/advisory paths with short conversation windows and a reranking step; RouteLLM-style trained classifier router — good idea long-term but needs labeled preference data this project doesn't have yet and conflicts with the zero-dependency goal if the package itself is vendored (steal the *idea*, not the package); real speculative decoding — solves a different problem (single-model-family latency), not cross-provider cost routing.
